01 · CONTEXT

Letters with personal data go out every month

Insurers send maturity notices, benefit payment confirmations and reinstatement notices by email. Each letter carries the policyholder's name, policy number and NIK, and every email copies the customer's servicing branch.

So there are two ways to get it wrong: the letter reaches the wrong customer, or the copy reaches the wrong branch. Under UU PDP (Law No. 27/2022), either one is a personal data protection failure that must be reported within 3 × 24 hours.

02 · PROBLEM

Every manual step is a chance for data to leak

In the manual process a person matches each PDF to the list, copies the address, types the branch CC, attaches and sends — about four minutes per letter, roughly ten hours per batch. There is no second check before sending and no record afterwards.

03 · INSIGHT

Leaks follow predictable failure modes

Because each manual step fails in a known way, each failure can be blocked by a specific, automated control. I designed thirteen, grouped by the question they answer.

Right document

  • DP-01Every customer has a letter
  • DP-02No duplicate letters
  • DP-03File name points to one policy
  • DP-04Policy, name and NIK match the recipient
  • DP-05No orphan letters

Right recipient

  • DP-06Email equals master data, no typo
  • DP-07Branch CC taken from branch master
  • DP-08One customer per email, no BCC

Data protected

  • DP-09Letter locked with the customer's password
  • DP-10No NIK in file name, subject or body
  • DP-11Logs and reports hold masked data only

Safe delivery

  • DP-12Official mailbox only, no credentials in code
  • DP-13File identical to the approved version
  • STOPKill switch halts the batch on anomalies
04 · SOLUTION

Validate, lock, and require two people before anything is sent

  1. Validate13 controls per letter
  2. QuarantineFailures never sent
  3. LockPassword = date of birth
  4. MakerReviews and submits
  5. CheckerA different person approves
  6. SendDry run, then 1 email per customer
  7. VerifyOutbox re-check and report

05 · GOVERNANCE

Enforced by the system, not by good intentions

Maker-checker

The maker submits; a different checker approves. The batch is fingerprinted at submission, so any later change forces a resubmission.

Kill switch

The batch halts if more than 20% is quarantined, if any file changes after approval, or if sending fails repeatedly.

Audit trail

Every validation, approval and email is logged with personal data masked. Every run scans logs and reports for raw NIK, email addresses and birth dates.

Documents

Risk & control matrix (16 risks), RACI and SOP, and an incident playbook with the UU PDP 3 × 24 hour notification.

08 · NEXT

Fix the exceptions at their source

The monthly control report does not only count exceptions; it points to where they come from.

  1. Build the send list directly from master data. Stale and mistyped emails were the top exception (DP-06).
  2. Remove the manual CC column from the template. Branch mailboxes come from branch master data only (DP-07).
  3. Enforce file naming at letter generation. Letter type + policy + period, never the NIK (DP-03, DP-10).

Then pilot one letter type in one branch, replace the assumed timings with a time study, move SMTP credentials into a secrets vault, and consider an SMS one-time password instead of the date of birth.
